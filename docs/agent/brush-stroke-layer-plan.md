# ブラシストロークレイヤー 計画書

Clip Studio Paintのベクターレイヤーのように、通常のブラシで描いた線を
記録し、拡大したときに新しい解像度で描き直せるレイヤーを、Solsticeに
追加する計画。2026年10月9日にユーザーの依頼で作成した。

## 目的と決定事項(ユーザー、2026年10月9日)

- **主な使い方:** 小さいサイズで描いた線画を拡大し、正式に使う。画像全体の
  拡大(画像の拡大縮小)で描き直せれば目的を満たす。変形ツールでの部分的な
  拡大は後回しにする。
- **消しゴム:** 消すストロークとして記録し、順番どおり再生する。CSPのような
  線単位の消去・交点までの消去は対象外(後の段階)。
- **本家Kritaとの互換:** 本家Kritaで開いたとき、通常のレイヤーとして
  見えればよい。互換性は努力義務で、難しい場合は考慮しない。

## 現状(コードで確認した事実)

| 項目 | 状態 | 場所 |
| --- | --- | --- |
| ベクターレイヤーへのブラシ描画 | ブラシツールが拒否する | `libs/ui/tool/kis_tool_freehand.cc` の `beginPrimaryAction()`(`nodePaintAbility()` が `VECTOR`) |
| ベクターレイヤーの描画先 | `paintDevice()` が `nullptr`。図形はflake(SVG、QPainter)で描く | `libs/ui/flake/kis_shape_layer.cc` |
| ブラシ入力の保存 | `KisPaintInformation::toXML()` / `fromXML()` がある | `libs/image/brushengine/kis_paint_information.h` |
| 決定的な再描画 | Solsticeのブラシプレビュー用に、乱数の種を固定して通常の描画経路(`FreehandStrokeStrategy`)で描く仕組みがある。全ダブの乱数はストロークの乱数源から取られる | `FreehandStrokeStrategy::setPreviewRandomSeed()`、`libs/ui/widgets/KisBrushStrokePreviewRenderer.cpp` |
| 画像の変形の受け口 | 外部レイヤー(`KisExternalLayer`)は `transform()`、`crop()`、`convertTo()` などで画像の拡大縮小・回転・反転・切り抜き・色空間変換を受ける。ファイルレイヤーやベクターレイヤーが使う | `libs/image/kis_external_layer_iface.h`、`libs/image/processing/kis_transform_processing_visitor.cpp` ほか |

既存のベクターレイヤーに統合しない理由: ベクターレイヤーは図形(SVG)を
QPainterで描く仕組みで、ブラシエンジン(`KisPainter`、ストローク、ダブの
並列描画)とは描画経路が別。ブラシの線を図形の一種にすると、flakeの描画の
中でブラシエンジンを動かすことになり、スレッドと更新の仕組みが合わない。

## 設計方針

- **専用レイヤー**(仮称 `KisBrushStrokeLayer`)を `KisExternalLayer` の
  派生として作る。描いた結果のキャッシュ(ペイントデバイス)と、線の記録を
  持つ。
- **描画中の見た目は通常どおり:** ブラシツールは通常のペイントレイヤーと
  同じようにキャッシュへ描き、同時に入力を記録する。描画中の見た目は変わらない。
- **記録するもの(1本ごと):**
  - 手ぶれ補正の後の点列(`KisPaintInformation`: 位置、筆圧、傾き、回転、
    時刻など)。補正の前の生の入力ではない(再生で補正をやり直すと線が変わる)。
  - 乱数の種。
  - ブラシのプリセット(設定と、先端画像・テクスチャなど必要なリソース)。
    同じプリセットを使う線は共有する。
  - 描画の状態: 描画色、合成モード(消しゴムを含む)、不透明度、
    パターン、グラデーション、ミラー描画など、ストロークが参照する画面の資源。
- **描き直し:** 画像の拡大縮小で `transform()` を受けたら、点の位置に
  変換を掛け、ブラシのサイズ(とテクスチャの倍率など、絶対値で持つ設定)に
  倍率を掛けて、全部の線を順に新しい解像度で描き直す。
- **元に戻す・線の削除:** 線の追加は、キャッシュに描いた結果をそのまま使う。
  線を取り除くときは、その線の範囲を消し、その範囲に重なる線を順に描き直す。
- **保存:** `.kra` に、レイヤーの種類、線のデータ、使ったプリセットを保存する。
  あわせて描画結果の画像も保存し、本家Kritaでは通常のレイヤーとして読める
  ことを目指す(努力義務)。

## 難所と対応

| 難所 | 対応 |
| --- | --- |
| 選択範囲で切り取られた線 | 最初はこのレイヤーで選択範囲による切り取りを使わない(描画を断るか、選択範囲を無視する)。必要なら後で選択範囲を線と一緒に保存する |
| 時間に依存するブラシ(エアブラシ、速度センサー) | 時刻を記録して再生する。最初の対象からは外す |
| 下地に依存するブラシ(Color Smudge、Clone、Filter、Deform、Mix など) | 対象外。このレイヤーでは使えないようにする |
| GPUのブラシ描画との差 | 最初はこのレイヤーでGPUのブラシ描画を使わない(CPUで描き、描き直しと同じ経路にする) |
| 画像の先端やテクスチャ | 拡大しても元画像の解像度以上には精細にならない。線の位置と太さは正しく描き直せる |
| 手ぶれ補正(特に遅延描画型のスタビライザー) | 補正後の点を記録する。記録する場所は描画のジョブを出す直前(`FreehandStrokeStrategy::Data`) |

## 段階

1. **技術検証(テストのみ、2026年10月9日、完了):** 下記。
2. **ブラシストロークレイヤー:** 通常のブラシツールで描けて線を記録し、
   画像の拡大縮小で描き直し、元に戻す・やり直し、保存・読み込みまで。
   対象は下地に依存しないPixel Brushの設定。
3. **線単位の編集:** 選択、移動、削除、色や太さの変更。
4. **CSPに近い編集:** 制御点の編集、交点までの消去、対応ブラシの拡大。

目的(小さい線画を同じ描き味のまま拡大して使う)は、段階2で達成できる。

## 段階2の設計(2026年10月9日、コードの調査後に確定)

当初の「`KisExternalLayer` の派生」は採らず、**`KisPaintLayer` の派生**
(`KisBrushStrokeLayer`、`libs/ui`)にする。理由:

- ペイントレイヤーの間接描画(Washモード、`KisIndirectPaintingSupport`)、
  GPUのWashプレビュー、投影の合成をそのまま使える。外部レイヤーでは、
  これらを作り直す必要がある。描画中の見た目と描き直しの結果をそろえるには、
  同じ描画経路が必要。
- `.kra` にはペイントレイヤーとして保存されるので、本家Kritaでは通常の
  ペイントレイヤーとして読める(互換性の要件を自然に満たす)。

仕組み:

- **記録:** `FreehandStrokeStrategy` が、描画先が `KisBrushStrokeLayer` の
  ときに、乱数の種を決め、描画のジョブ(点・線分・曲線)と描画の状態
  (プリセットの複製、描画色・背景色、合成モード、不透明度、表示倍率、
  パターン、グラデーション、ミラー描画の本数、描画時のデバイスの位置)を
  記録する。詳細度(LOD)の下書きは記録しない。
- **元に戻す:** 線の記録を加えるコマンドを、ストロークの元に戻すコマンド
  (`KisPainterBasedStrokeStrategy` の親コマンド)に加える。画素の変更と
  記録が1回の操作で一緒に戻る。
- **座標:** 描画時のデバイスの位置を記録し、描き直しでは現在の位置との差を
  足す。移動ツールでレイヤーを動かしても、線の記録はずれない。
- **ほかのツール:** ブラシツール以外のペイントツールは、このレイヤーに
  描けない(`KisTool::nodePaintAbility()`)。フィルタや塗りつぶしなど、
  ほかの経路の変更は記録されない。
- **描き直しの安全策(2b):** 拡大の前に、記録を今の大きさで描き直して
  レイヤーの画素と比べる。一致すれば新しい解像度で描き直し、違えば
  (記録されない変更、選択範囲での切り取り、アルファロックなど)通常の
  ペイントレイヤーと同じ画素の拡大にする(記録はそのまま残すが、画素と
  一致しないので以後も画素の拡大になる)。黙って
  変更を失うことはない。段階1で、同じ大きさの描き直しが画素単位で一致する
  ことを確かめてある。

小分けの段階:

- **2a:** レイヤーの種類、レイヤーの追加(レイヤーパネルの追加メニュー)、
  ブラシの線の記録と元に戻す、テスト(実際の描画経路で描いた線の記録を
  描き直すと画素が一致する)。
- **2b:** 画像の拡大縮小での描き直しと安全策。
- **2c:** `.kra` への線の記録の保存と読み込み。

## 段階2bの実装結果(2026年10月9日)

| 場所 | 内容 |
| --- | --- |
| `libs/image/KisRedrawableLayerInterface.{h,cpp}`(新規) | 変形のときに画素の変換の代わりに描き直せるレイヤーの口。`createTransformRedrawCommand(QTransform)` が描き直しのコマンド、できなければ nullptr。デストラクタを外に置いて、型情報を kritaimage に持たせる(ライブラリをまたぐ `dynamic_cast` のため) |
| `libs/image/processing/kis_transform_processing_visitor.{h,cpp}` | `visit(KisPaintLayer*)` の最初で、選択範囲がなければこの口に `KisTransformWorker::transform()` を渡して聞く。コマンドが返れば画素の変換をせずに使う。選択範囲を `m_selection` に保持 |
| `libs/ui/KisBrushStrokeLayer.{h,cpp}` | 口の実装、`transformedStrokes()`(位置の変換、ブラシサイズとテクスチャの倍率を `sqrt(|det|)` 倍、記録の位置をデバイスの位置に)、記録の差し替えコマンド |
| `libs/image/CMakeLists.txt` | 新しいソース |

描き直しの条件と手順:

1. 記録がある、アニメーションのレイヤーでない、選択範囲がない、変換が
   拡大縮小と移動だけ(`type() <= TxScale`、反転なし)。回転や反転、選択範囲
   付きの変形は画素の変換。
2. 記録を今の大きさで描き直し、`exactBounds()` の範囲でレイヤーの画素と
   比べる(各8ビットのチャンネルで差3まで。色はアルファを掛けた値で
   比べる)。違えば画素の変換にし、理由(違う画素の数、差の最大、範囲)を
   警告と `KisUsageLogger`(`%APPDATA%\Solstice\logs\krita.log`)に書く。
   記録しない線(点・線分・曲線以外のジョブ)もログに書く。
   透明な画素の色を比べないのは、ぼかし(Color Smudge)のブラシが透明な
   画素の色を描き直しと違う値で残すため(RGBA float の文書で、透明な
   画素が黒と白で食い違い、拡大が画素の拡大になっていた。2026年10月9日)。
3. 変換した記録を描き直し、記録の差し替えと、デバイスを消して描き直した
   画素を写す `KisTransaction` を1つのコマンドにまとめる。元に戻すと記録と
   画素が一緒に戻る。

これにより Image > Scale Image(画像の拡大縮小)と Layer > Scale Layer
(`KisTransformProcessingVisitor` を使う経路)が描き直しになる。変形ツールは
別の経路で、下の「変形ツールでの描き直し」で対応した。

テスト `KisBrushStrokeLayerTest`(7件、通過): 4倍の拡大で記録の位置が4倍に
なり、レイヤーの画素が記録の描き直しと一致する。半透明の画素の割合は
描き直しが0.15、普通のペイントレイヤーの画素の拡大が0.54。元に戻すと記録と
画素が元に戻る。ブラシ以外の変更(塗りつぶし)があるレイヤーは画素の拡大に
なり、記録は変わらない。`kis_processings_test`、`kis_image_test` も通過。
描き直しは画像の処理の中で別の画像のストロークを走らせて待つが、テストでは
詰まらなかった。

既知の制限: 画像の切り抜き(Crop)は画素だけを切るので、切り抜いた後に
拡大すると、範囲外の線も描き直される(画面外のため見えない)。

手動確認の項目(2b、2026年10月9日に問題なし):

1. 小さく描いた線画で Image > Scale Image を拡大すると、普通のペイント
   レイヤーよりくっきりする。ブラシの太さは拡大に比例する。
2. 元に戻す・やり直しで、大きさと線が一緒に戻る。戻した後にまた描ける。
3. フィルタを掛けたレイヤーは、拡大すると普通の画素の拡大になる(変更が
   失われない)。
4. Layer > Scale Layer でもくっきり拡大する。回転や反転は画素の変換。

ファイルの形式(`QDataStream`、Qt 5.15、リトルエンディアン、倍精度):
マジック `SBSL`、版 1、プリセットの表、パターンとグラデーションの表、
線の一覧。線はプリセットとリソースを番号で指す。

- **プリセット:** `KisPaintOpPreset::toXML()` と同じ形
  (`paintopid`、`name`、設定)。同じプリセットは1回だけ書く。
  `toXML()` を直接使わないのは、リンクされたリソースの検索と書き出しが
  リソースのデータベースを使い、GUIスレッド専用で、`.kra` の保存が
  別スレッドで走るため。
- **リソース(2026年10月10日にブラシ先端を追加):** プリセットのリンクされた
  リソース(ブラシ先端、テクスチャ、マスクブラシの先端)と、線のパターンと
  グラデーションを、リソースのファイルごと表に書く(種類・md5・ファイル名で
  重複を省く)。リンクされたリソースは、記録したプリセットのリソースの
  スナップショット(`KisLocalStrokeResources`)から取るので、データベースを
  使わない。`isSerializable()` でないもの(ABRの先端)はファイルなしで書く。
  読み込みは `KisResourceLoaderRegistry` の、種類とファイル名の
  MIMEタイプに合うローダーで作る。ファイルがない、または読めなければ、署名で
  インストール済みのものを探す。形式の版は1のまま(表の構造は同じで、
  前の版の読み込みは知らない種類をインストール済みから探すだけ)。
- **色:** 色モデル、ビット深度、プロファイル名、生のバイト(正確に戻る)。
- **ブラシ入力:** 位置、筆圧、傾き、回転、接線方向の筆圧、遠近、時刻、速度、
  キャンバスの回転と反転、傾きの向きの補正。`KisPaintInformation::toXML()`
  はキャンバスの回転などを含まないので使わない。
- 読み込んだプリセットは、線の色・パターン・グラデーションを使って
  リソースのスナップショットを作る(`cloneWithResourcesSnapshot()`)。
  リソースの検索先は、ファイルに保存されたリソースと、そこにない分を
  インストール済みから探したものだけの `KisLocalStrokeResources`。
  インストール済みのものより、描いたときと同じ保存されたものを使う。記録した
  プリセットと同じく、描き直し(画像の処理のスレッド)でGUIスレッド専用の
  検索をしない。キャンバスのリソースを必要としないプリセットは、1つの
  スナップショットを共有する。
- 新しい版、壊れたデータ、途中で切れたデータは読まない(一部だけ読んだ
  記録は使わない)。ブラシエンジンがないプリセットの線は外す。どちらの
  場合も、記録と画素が一致しなくなるので、拡大は画素の拡大になる(2bの

描き直しが毎回同じになるように(2026年10月10日): 手動確認で、ライブの
線と描き直しが輪郭だけ食い違い(数千画素、差は最大116)、拡大が画素の拡大に
なった。原因は、Pixel Brush の点(dab)の画像が複数のスレッドで作られ、
乱数で画像を選ぶgih(`sel0:random`。この例ではマスクブラシの
`rock_pitted.gih`)が、線で共有する乱数の源をスレッドの順番で引くこと。
同梱の `c) Pencil-4 Soft`(`graphite_grain.gih`)では、乱数以外の原因も含めて
描き直し同士でも結果が変わった(1スレッドに制限すると一致)。

対応: `KisPainterBasedStrokeStrategy::setSequentialDabRendering()`。
`initPainters()` でペインターに渡す並列処理の口を、並列のジョブを順番の
ジョブに包み直すもの(`SequentialRunnableJobs`)にする。記録中の線
(`FreehandStrokeStrategy::initRecording()`)と描き直し(`drawStroke()`)で
有効にする。普通のペイントレイヤーは従来どおり並列。マスクブラシの
ペインターには並列処理の口がなく、もともと順番に描く。このレイヤーでは
大きなブラシの描画が遅くなりうる。

試した別案(採らなかった): 点ごとに乱数の源を作り、種を線のスレッドで
共有の源から引く(`KisBrushOp::paintAt()`)。マスクブラシの例は直るが、
`c) Pencil-4 Soft` は乱数以外の競合で直らなかった。

この変更より前に記録した線(ランダムなgihなど)は、記録とライブの画素が
一致しないので描き直せない(画素の拡大になる)。

線の始まりの記録(同日): 順番の描画にした後も、手動確認でテクスチャとマスク
ブラシの線(`z) 线稿 纹理`)が輪郭だけ食い違った(線1本、2996画素)。テストで
記録した点の列をライブとして流し直すと一致し、アプリのライブだけが違った。
原因は、ブラシツール(`KisToolFreehandHelper::initPaint()`)が、点の間隔の
計算(`KisDistanceInformation`)を、ホバー中の最後のカーソル位置と向き、
間隔の更新間隔(サイズなどがセンサーで変わるブラシでは
`SPACING_UPDATE_INTERVAL`)から始めること。描き直しは空の状態から始めて
いたので、点の並び全体がずれた(内側は塗りつぶされて同じ、輪郭が違う)。

対応: `KisRecordedBrushStroke::starts`(ミラーの各写しの始まり: 直前の点の
有無、位置、向き、間隔と時間の更新間隔、点の通し番号)。
`FreehandStrokeStrategy::initRecording()` が `KisFreehandStrokeInfo::dragDistance`
から記録し、`drawStroke()` がその `KisDistanceInformation` で始める。変形では
位置と向きも写す。保存形式は版2(線ごとに始まりの一覧)。版1のファイルは
始まりなしで読む(新しい形式は前の版では読めず、画素だけのレイヤーになる)。

テスト `testStrokeStartRecorded`: ホバーの位置と向きから始めた鉛筆の線が、
描き直しで一致し、始まりを外すと一致しない。始まりは保存して読める。

## 変形ツールでの描き直し(2026年10月10日)

変形ツール(Free Transform)で拡大縮小と移動だけをしたとき、適用の時点で
線を描き直す。

| 場所 | 内容 |
| --- | --- |
| `libs/image/KisRedrawableLayerInterface.h` | `createTransformRedrawCommand()` に `original`(変形前の内容)を追加。変形ツールでは、レイヤーのデバイスはプレビューを表示しているので、変形前の画素はツールのキャッシュにある。2bの経路(`KisTransformProcessingVisitor`)はデバイスそのものを渡す |
| `libs/ui/KisBrushStrokeLayer.{h,cpp}` | 記録と照合するのは `original`、描き直した画素はデバイスに書く(デバイスを消してから写す) |
| `plugins/tools/tool_transform2/strokes/inplace_transform_stroke_strategy.{h,cpp}` | `redrawRecordedStrokes()`: `finishAction()` で最後の更新の後に順番に実行するジョブを加える。その時点の `currentTransformArgs` が Free Transform なら、`KisTransformUtils::MatricesPack::finalTransform()` で描き直す。コマンドは `Transform` のグループに加え、ストロークの元に戻すに入る。プレビュー中は従来どおり画素の変換(描き直しは重いので、確定時の1回だけ) |
| `plugins/tools/tool_transform2/strokes/transform_stroke_strategy.cpp` | オーバーレイのプレビュー(設定)の経路: 確定時の画素の変換の代わりに描き直す。できなければ従来の画素の変換 |

条件: 選択範囲なし、外部の画像の変形でない、Free Transform、変換が
拡大縮小と移動だけ(2bと同じ判定)、記録と変形前の画素が一致。

注意: 変形の引数は、確定時(`finishAction()`)ではまだ最後の更新が反映されて
いないことがある(更新はタイマーで間引かれる)。ジョブの中で
`currentTransformArgs` を読む。

テスト `KisBrushStrokeLayerTransformTest`(新規、`kritatooltransform_static`
をリンク): 実際の `InplaceTransformStrokeStrategy` で1.8倍にすると、記録が
変換に従い、画素が記録の描き直しと一致する。元に戻すと記録と画素が戻る。
回転は画素の変換で、記録は変わらない。テストでは、更新の強制
(`KisAsynchronousStrokeUpdateHelper::UpdateData(true)`)が必要。ストロークが
開いている間に `image->waitForDone()` を呼ぶと終わらない。

あわせて `testSmudgeOverStroke` の画像の比較を、アルファを掛けた値の比較に
した(透明な画素の色の違いで、乱数の種によって失敗していた)。

手動確認の項目(変形ツール、2026年10月10日に問題なし):

   くっきりする。ドラッグ中のプレビューはぼけていてよい。
2. 元に戻す・やり直しで、大きさと線が一緒に戻る。
3. 回転して適用すると、普通の画素の変換になる。その後に拡大すると、

## 選択範囲の移動と記録の照合(2026年10月13日)

きっかけ: ユーザーのファイルで、拡大後にレイヤーがくっきりしなかった。
ログは「its pixels are not its 250 recorded strokes (18760 ... pixels
differ ...)」。ファイルの写しで記録を描き直して照合すると、全部の線が同じ
プリセットで、一致しない線は自分の画素の100%が違い(位置と傾きがずれる)、
ほかの線は完全に一致した。頭と手足の線だけで、フリーハンドの選択範囲と
移動ツールで形を直した場所。移動ツールの選択範囲の移動
(`MoveSelectionStrokeStrategy`)は画素だけを切り取って貼り、記録を
動かさないので、拡大の照合で外れ、画素の拡大になった。気付けるのは
拡大の後だけだった。

### 1. 選択範囲の移動で記録も動かす

| 場所 | 内容 |
| --- | --- |
| `libs/ui/KisBrushStrokeLayer.{h,cpp}` | `createSelectionMoveCommand(mask, offset)`: 線ごとに選択範囲との関係を判定する(`selectionCoverage()`)。中にある線は `transformedStrokes()` で平行移動し、記録の最後に並べる(移動した画素は残りの上に貼られる)。境界をまたぐ線があれば nullptr(記録は変えず、ログに理由)。`SetStrokesCommand` で元に戻せる |
| `plugins/tools/basictools/strokes/move_selection_stroke_strategy.cpp` | `finishStrokeCallback()`: レイヤーが `KisBrushStrokeLayer` なら、移動前の位置に戻した選択範囲の写しでコマンドを作り、ストロークの元に戻すに加える |

判定(`selectionCoverage()`): ダブの中心の範囲をブラシのサイズ+4画素
広げた矩形が選択範囲と交わらなければ外、全部が完全に選択されていれば中。
どちらでもなければ、その線だけを描いた画素で判定する: アルファ a と選択の
値 s(0〜255)で、中は全画素で a×(255−s) ≤ 3×255、外は a×s ≤ 3×255
(描き直しの照合の許容差3に合わせる)。

順番を最後にする理由: 通常の合成(over)は結合的なので、中の線の合成を
外の線の上に置くことは、中の線を外の線の後に1本ずつ描くことと同じ。
消しゴムなど over 以外の線が絡むと一致しないことがあり、下の照合で
分かる。

変形ツールの選択範囲つきの変形は対象外(画素の変換のまま。照合で
知らせる)。

### 3. 記録が使えなくなったら知らせる(バックグラウンドの照合)

`KisBrushStrokeLayerMonitor`(`KisBrushStrokeLayer.cpp`、GUIスレッド):

- **きっかけ:** レイヤーの `setDirty()`(上書き)と `setStrokes()` が
  照合を頼む(`requestRecordCheck()`: フラグを立て、ペイロードのない
  キュー呼び出しでモニターを起こす。1.5秒の待ち)。
- **探し方:** `KisPart::documents()` の画像から、頼んだレイヤーを探す。
  画像が待機中(`isIdle()`)でなければ1秒後にもう一度。開いている文書に
  ないレイヤー(テストの画像、元に戻すの中のレイヤー)は照合しない。
- **省略:** 記録したブラシの線(`KisRecordBrushStrokeCommand`)と描き直し
  (`SetStrokesCommand` の `recorded`)は `markChangeRecorded()` で
  印を付け、状態が分かっている(Unknown でない)なら照合しない。
  ブラシの線は一致を保ち、一致しないレイヤーを一致させることもない。
  選択範囲の移動の `SetStrokesCommand` は印を付けない(照合する)。
- **照合:** デバイスの写し(タイルは書き込み時に複製)と記録を、専用の
  `QThreadPool`(1スレッド)で `strokesMatchPixels()`(拡大の照合と同じ
  `sameContent()`)。結果は、その間に変更がなかった(世代 `m_generation`
  が同じ)ときだけ使う。
- **表示:** 一致しなくなったら、キャンバスのメッセージ(7秒、High)と
  ログ、Layers のアイコンを警告に替える(`icon()` が `warning` を返す。
  Layers はこのアイコンをサムネイルの角に約12画素で描く
  (`NodeDelegate::drawDecoration()`、`decorationSize()`)ので、ブラシに
  小さな印を重ねる最初の案は見えなかった。`baseNodeChangedCallback()` で
  更新)。元に戻すなどで一致に
  戻ったら、そのメッセージ。Unknown から一致は黙って。
- **時間:** ユーザーのファイルの 251本で約1.5秒(テストの計測)。

寿命の注意(実装中に踏んだ):

- キューに積むイベントにノードの強い参照(`KisNodeSP`)を持たせると、
  終了時に Qt がイベントの錠を持ったままイベントを破棄し、レイヤーの
  デストラクタ(`QObject` の後始末が同じ錠を取る)で止まる。依頼も結果も
  生の値だけを運ぶ。照合中のレイヤーはモニターの `m_running` が保つ。
- モニターは破棄しない。`aboutToQuit` で照合の終わりを待つ。
- `KisBrushStrokeLayer` のメンバーを増やしたら、インストール済みの
  プラグイン(.kra の読み込みなど)も作り直す。テストは `_install` の
  プラグインを読むので、古いプラグインが古い大きさでレイヤーを確保し、
  ヒープを壊す(`testKraRoundTrip` がメタデータのプラグイン読み込みで
  落ちた)。

### テクスチャの位置(同日、手動確認で判明)

手動確認で、警告になったレイヤーが、元に戻しても拡大で画素の変換になった。
ログは「28628 of 362231 pixels differ, by up to 25」(線の画素の不透明度が
両方向に数段階違う)。ファイルの写しで調べると、記録の描き直しは毎回同じで、
テスト環境で記録のジョブをライブとして流し直しても(GPUの有無とも)
描き直しと一致した。違いは、このレイヤーの「Paint Test 2」にテクスチャ
(`26okqfbu.bmp`)があり、描いた後にレイヤーを (1,−111) 動かしていたこと。

原因: ブラシのテクスチャはキャンバスに固定されている
(`KisTextureOption::apply()`: 画像の点 X の下の模様は X − OffsetX、模様の
大きさで折り返す。GPUの `gpuDescription()` も同じ)。描き直しは記録の
位置を動かして描くので、模様の別の場所を拾っていた。レイヤーの移動、
選択範囲の移動、拡大縮小のすべてで起きる(テクスチャのないブラシでは
起きないので、最初のファイルでは見えなかった)。

対応: `mapTexture()`(`KisBrushStrokeLayer.cpp`)。点を shift 動かしてから
変換 T(拡大縮小と移動)で描くとき、模様の倍率を T の倍率倍にし、
`Texture/Pattern/OffsetX/Y` を s × offset + T(shift) にする(丸める)。
`drawStroke()`(描き直しと照合)と `transformedStrokes()`(記録の変換)の
両方で使う。ストロークごとのランダムなオフセット(`isRandomOffsetX/Y`)は
追従できない。修正後、ユーザーのファイルの「Brush Stroke Layer 2」は
記録の描き直しと完全に一致した(0画素)。

テスト `testTextureFollowsMovedStrokes`: テクスチャのある同梱のPixel Brush
(ランダムなオフセットなし、今は `c) Pencil-5 Tilted`)で描き、レイヤーを
(7,−5) 動かしても、選択範囲で (13,9) 動かしても、記録の描き直しが画素と
一致する。修正を外すと失敗する(645画素、差は最大185)。

テスト `KisBrushStrokeLayerTest`(18件、通過):
`testSelectionMoveMovesStrokes`(黒い線を選択範囲で赤い線の上に動かすと、
記録が動いて最後に並び、描き直しが画素と一致する。元の順番では一致しない。
線を切る選択範囲では nullptr。元に戻すと記録が戻る)、
`testRecordCheckFindsOtherEdits`(開いた文書のレイヤーで、描いた後に一致、
塗りつぶすと不一致、取り消すと一致に戻る)。

手動確認の項目(2026年10月13日に問題なし。印はアイコンの置き換えに変更、
テクスチャの位置を修正した後):

1. ブラシストロークレイヤーで、線を丸ごと囲むフリーハンドの選択範囲を
   移動ツールで動かし、Image > Scale Image で拡大すると、くっきりする。
2. 線を途中で切る選択範囲で動かすと、数秒以内に「no longer matches」の
   メッセージが出て、Layers のアイコンに警告の印が付く。元に戻すと
   「matches again」が出て印が消える。
3. フィルタ(ぼかしなど)を掛けても同じく知らせる。ブラシで描くだけでは
   メッセージが出ない。
4. ユーザーの `20261011.kra` を開くと、数秒で2つの「Brush Stroke Layer 1」
   に警告の印が付く(記録と画素がすでに一致しない)。
5. 描画中や大きなファイルで、照合による引っかかりがない。

## 一致しない部分だけ画素で拡大する(2026年10月13日、案A)

これまでは、記録と画素が1画素でも違えば、拡大でレイヤー全体を画素の変換に
していた。一部だけ選択範囲で動かした線画でも全体がぼけた。拡大のときに
一致しない部分だけを画素の変換にする(記録の形式と元に戻すは変えない)。

| 場所 | 内容 |
| --- | --- |
| `libs/image/KisRedrawableLayerInterface.h` | `createTransformRedrawCommand()` に `PixelTransform transformPixels`(呼び出し側が画素を変換するのと同じ方法で、デバイスを変換した新しいデバイスを返す関数)を追加 |
| `libs/image/processing/kis_transform_processing_visitor.cpp` | 写したデバイスに同じ引数とフィルタの `KisTransformWorker` |
| `plugins/tools/tool_transform2/strokes/inplace_transform_stroke_strategy.cpp`、`transform_stroke_strategy.cpp` | `KisTransformUtils::transformAndMergeDevice()`(その時点の変形の引数、ノードの `ProgressHelper`) |
| `libs/ui/KisBrushStrokeLayer.cpp` | `sameContent()` が違う画素の範囲(`KisPixelSelection`)と、違う画素数・どちらかが覆う画素数を返せる。`createTransformRedrawCommand()` の部分的な合成。メッセージは `postImageMessage()`(画像のポインタは比べるだけ。生の値だけをキューに積む) |

手順: 今の大きさで記録を描き直して照合し、違う範囲 M を得る。違う画素が
覆う画素の半分を超える(または描くものがない、`transformPixels` がない)
なら従来どおり nullptr(全体を画素の変換)。それ以外は、変換した記録を
描き直し、M を2画素広げ(`KisGrowSelectionFilter`、縁の半透明を含める)、
元の画素と M を `transformPixels` で変換し、M を倍率(最低1)画素で
ぼかし(`KisFeatherSelectionFilter`)、描き直しの上に画素の変換を
`COMPOSITE_COPY` と M の選択範囲で写す(選択の値で補間)。記録は変換した
線に差し替える(M の部分は記録と一致しないままなので、次の拡大でも同じく
その部分が画素の変換になる)。ログと、キャンバスのメッセージ(画素で
拡大したおおよその割合)。

性質と制限: 一致しなくなった後に描いた線も、M の中を通る部分は画素の
変換になる(重なり順を保つには記録に画素の項目を入れる案Bが要る)。
描き直しと画素の変換は位置が一致するので、境目で線はずれない。

確認: ユーザーのファイルの写しで、選択範囲で動かした頭の輪郭だけが画素の
拡大になり、ほかの線と胴体はくっきり、境目は目立たない(テスト用の一時的な
プログラムで2倍)。

テスト `KisBrushStrokeLayerTest`(19件、通過): `testScaleRedrawsAroundOtherEdits`
(線の端に塗りつぶしを加えて4倍: 記録は4倍になり、塗りつぶしの内側は画素の
拡大と同じ、離れた部分は記録の描き直しと同じで画素の拡大とは違う)、
`testScaleFallsBackAfterOtherEdits`(大部分を塗りつぶすと、従来どおり全体が
画素の拡大で記録は変わらない)。`KisBrushStrokeLayerTransformTest`、
`kis_processings_test`、`MoveSelectionStrokeTest` も通過。

手動確認の項目(2026年10月13日に問題なし):

1. 線画の一部を、線を途中で切る選択範囲で動かしてから Image > Scale Image で
   拡大すると、動かした部分だけ少しぼけ、ほかはくっきりする。「drawn again,
   except about N%」のメッセージが出る。
2. フィルタを一部に掛けたレイヤーも同じ。大部分にフィルタを掛けると、全体が
   画素の拡大になる。
3. 変形ツール(Free)で拡大して適用しても同じ。元に戻すで大きさと線が戻る。
4. 境目に段差や継ぎ目が目立たない。

## 段階1: 技術検証

テスト `KisBrushStrokeReplayTest`
(`plugins/paintops/defaultpaintops/brush/tests/`)で、記録した点列から
線を描き直せるかを確かめる。既存の機能には触れない。

- **点列:** 筆圧が変わるS字の線を、補正後の点列として合成する
  (位置、筆圧、時刻)。
- **描画:** 通常の描画経路(`FreehandStrokeStrategy`、乱数の種を固定)で、
  点の間を線分として描く。
- **確かめること:**
  1. **再現性:** 同じ点列・同じ種で2回描くと、画素が完全に一致する。
  2. **4倍での忠実さ:** 位置とブラシのサイズを4倍にして描いた結果を
     1/4に縮小すると、等倍で描いた結果とほぼ一致する。
  3. **4倍でのくっきりさ:** 輪郭のぼけ(半透明の画素の割合)が、等倍の結果を
     4倍に拡大した画像より明らかに小さい。
- **対象のブラシ:** Krita 4の同梱プリセットから、自動先端の筆圧サイズ
  (`b)_Basic-5_Size_default`)、インク(`d)_Ink-2_Fineliner`、
  `d)_Ink-3_Gpen`)、鉛筆(`c)_Pencil-2`)、画像先端の荒いインク
  (`d)_Ink-7_Brush_Rough`)。

### 技術検証の結果(2026年10月9日)

`KisBrushStrokeReplayTest` は7件すべて通過。数値はテストの出力
(半透明率 = 線の画素のうち不透明度10〜90%の画素の割合)。

| ブラシ | 再現性 | 4倍を1/4に縮小 vs 等倍(不透明度の差、平均 / 最大、0〜255) | 半透明率: 4倍で描き直し / 等倍を4倍に拡大 |
| --- | --- | --- | --- |
| 自動先端、筆圧サイズ(`b)_Basic-5_Size_default`) | 一致 | 2.78 / 145 | 0.022 / 0.122 |
| インク(`d)_Ink-2_Fineliner`) | 一致 | 2.98 / 254 | 0.099 / 0.576 |
| インク(`d)_Ink-3_Gpen`) | 一致 | 2.42 / 170 | 0.111 / 0.554 |
| 鉛筆、テクスチャあり(`c)_Pencil-2`) | 一致 | 0.28 / 14 | 0.774 / 0.804 |
| 画像先端の荒いインク(`d)_Ink-7_Brush_Rough`) | 一致 | 4.27 / 233 | 0.030 / 0.163 |

分かったこと:

- **再現性:** 同じ点列と乱数の種で、どのブラシも画素単位で同じ線になる。
- **忠実さ:** 4倍で描いた線を縮小すると、等倍の線と平均ではほぼ一致する
  (平均の差は最大でも255中4程度)。最大の差が大きいのは、細い入り抜きの
  先端など、等倍では1画素未満になる部分の画素の割り当てが変わるため。
- **くっきりさ:** 線画向けのブラシでは、4倍で描き直した線の輪郭は、等倍の線を
  拡大した画像より半透明の画素が5〜6倍少ない(目視でも輪郭がはっきりし、
  入り抜きも保たれる)。テクスチャが主体の鉛筆は、線の内部も半透明なので
  この指標では差が出ない(想定どおり。テクスチャ自体は拡大しても精細に
  ならない)。
- **設計への反映:** 実際のフリーハンドツール(`KisToolFreehandHelper`)は、
  手ぶれ補正の方式によって点だけでなく曲線(`paintBezierCurve()`、制御点
  付きの `FreehandStrokeStrategy::Data`)も送る。記録は点列ではなく、
  **描画のジョブ(点・線分・曲線と制御点)をそのまま**記録する。
- **未検証:** 実際のツール操作からの記録、GPUのブラシ描画との一致、時間に
  依存するブラシ、合成モードと消しゴム。段階2で確かめる。

画像を確かめるときは、`SOLSTICE_REPLAY_DUMP=<フォルダ>` を付けて
テストを実行すると、各ブラシの等倍・4倍・等倍を拡大した画像を書き出す。
